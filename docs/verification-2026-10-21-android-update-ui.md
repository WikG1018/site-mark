## 已落实的改进

| 范围 | 发现与处理 |

| 工程验证 | 更新旧性能测试中的列表与筛选定位；新增真实图片字节的模拟器截图验收；排除生成的 build 输出，避免构建后静态分析误扫独立生成包 |

## 复跑入口

- 全量回归：`flutter test --no-pub --timeout 2m`
- 原生测试：在 `android/` 执行 `gradlew :sitemark_system_api:testDebugUnitTest`
- 布局截图：`flutter drive --driver=test_driver/ui_audit_driver.dart --target=integration_test/ui_audit_test.dart -d <测试模拟器>`
- 截图输出：`.dart_tool/ui-audit/screenshots/<SITEMARK_AUDIT_LABEL>/`
- 安装器验证：`integration_test/update_installer_test.dart`；仅用于无真实数据的测试模拟器，文件准备约定见测试文件头部。先安装测试宿主，再把同签名、更高版本的夹具放入私有缓存；驱动使用 `--keep-app-running`，否则 Flutter 会在结束时卸载宿主并清空夹具。

## 尚未验证的边界

- 尚未运行本轮远程 CI，不能把本地通过表述为 CI 全绿。
- 未进行真实外网 APK 的整包下载验收；网络与错误分支使用受控字节流测试，真实安装入口单独在模拟器验证。

- Android 12 / 17 真机、厂商安装授权界面、杀进程中断下载、正式签名覆盖升级仍需发布前真机复验。
- 不保证进程被杀后断点续传；当前明确提示重新下载。未变更 NAS、备份恢复和 Rust 核心，本轮没有新增它们的真实服务器/设备验收。
- iOS 与鸿蒙未做设备验收；Swift 仅同步了 Pigeon 声明，没有接入 Android 安装能力。

结论：本轮修复已通过上述本地门禁，可以提交 PR 进入 CI 和代码审查；不能据此宣称所有机型、所有外部服务或正式升级已经全部验证。

## 2026-10-22 发布前补充：真实照片处理回归

在无真实用户数据的 API 35 模拟器安装正式签名 v1.0.31 通用包，创建合成项目
`Release-Upgrade-Audit`，调用 AOSP 系统相机（虚拟场景，不使用电脑摄像头）拍摄。
原图是 73,034 字节的 JPEG，尺寸 1392×1856，但后台处理失败。

用同一原图调用真实 Rust 渲染器，明确复现
`invalid_data:validate render request: photo number exceeds 32 characters`。
原因是 Dart 早已生成带项目名的编号、按最终文件名 255 UTF-8 字节限制，
Rust 渲染输入却仍沿用旧的 32 字符上限。改为有界且兼容当前/历史编号的输入限制，
不改变编号、不重命名已有文件，也不改变水印内容。

- 新增真实 JPEG 渲染回归：长英文、中文、表情字符和旧版带 UUID 编号；输出摘要匹配，原图摘要不变。
- 保留过长恶意输入的边界测试，不移除输入限制。
- Android 集成测试新增 Dart 编号生成 → 真实 Rust 渲染 → 文件及摘要校验，不再仅依赖假的图像处理层。
- 脱敏诊断增加 `invalidRenderRequest`，避免把参数契约错误误归类成图片损坏；不记录字段值或路径。
- 同一相机原图在本机真实 Rust 渲染成功，输出 1392×1856。正式签名覆盖升级、旧失败记录重试和新拍摄的结果需在发布资产完成后补记。

该问题由独立发布前测试确认，不能据此断言此前同事手机的所有失败都是同一原因。
